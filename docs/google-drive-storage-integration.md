# Google Drive file storage integration\n\n## Purpose\n\nLearner's Guide keeps Supabase PostgreSQL, Supabase Auth, RLS, role permissions, and existing application relationships. Google Drive stores the actual educational files.\n\nThe browser never receives Google OAuth client secrets or refresh tokens.\n\n## Storage model\n\n- Supabase tables keep file metadata and the provider file identifier.\n- Existing storage_path / legacy fields remain during migration.\n- New Google-backed records use storage_provider=google_drive.\n- storage_file_id contains the private Google Drive fileId.\n- storage_status tracks lifecycle state.\n- storage_upload_id makes an upload operation uniquely traceable.\n- storage_checksum stores the provider checksum when available.\n\n## Backend\n\nsupabase/functions/file-storage is the secure file gateway.\n\nOperations:\n- init-upload\n- finalize-upload\n- download\n- delete\n- rename\n\nThe function verifies the Supabase bearer token, uses the existing RLS-visible record as the authorization check, and only then uses the server-side Google credential.\n\n## Google credentials\n\nStore these only as Supabase Edge Function secrets:\n- GOOGLE_CLIENT_ID\n- GOOGLE_CLIENT_SECRET\n- GOOGLE_REFRESH_TOKEN\n- GOOGLE_DRIVE_ROOT_FOLDER_ID\n- optional GOOGLE_DRIVE_MATERIALS_FOLDER_ID\n- optional GOOGLE_DRIVE_HOMEWORK_FOLDER_ID\n- FILE_STORAGE_ALLOWED_ORIGINS\n\nNever commit any of these values to GitHub or put them in frontend code.\n\n## OAuth scope\n\nThe intended minimum scope is https://www.googleapis.com/auth/drive.file.\n\nThe application should create and manage its own dedicated Drive folders/files so it does not need broad access to unrelated Drive content.\n\n## Upload flow\n\n1. User selects a file.\n2. Browser calls file-storage:init-upload.\n3. Backend verifies the current user and existing RLS access.\n4. Backend creates a pending application record.\n5. Backend allocates a Google Drive file ID.\n6. Backend starts a Google Drive resumable upload session.\n7. Browser uploads file bytes to that session in chunks.\n8. Browser calls finalize-upload.\n9. Backend reads the Drive file using the server-side credential.\n10. Backend verifies the Drive ID, application upload tags, expected folder, filename, size, and MIME type.\n11. Only then is the database row marked complete.\n\nGoogle recommends resumable uploads for large/mobile uploads and exponential backoff for transient rate-limit/server failures.\n\n## Download flow\n\n1. Browser sends entity + recordId.\n2. Backend verifies the Supabase user.\n3. Backend reads the record through the user's RLS scope.\n4. Backend obtains the stored Drive file ID.\n5. Backend verifies the Drive file exists and is not trashed.\n6. Backend streams the private Drive file to the browser.\n\nNo public Drive URL is created.\n\n## Delete flow\n\n1. Verify application authorization.\n2. Mark metadata as deleting.\n3. Trash the Drive file.\n4. Remove the application record.\n5. If any step fails, preserve an error state so reconciliation can repair it.\n\n## Partial failures\n\n### Drive succeeds, database fails\n\nThe record remains traceable through the upload ID and Drive application metadata and is eligible for reconciliation.\n\n### Database succeeds, Drive fails\n\nThe record becomes failed; it is not presented as a completed file.\n\n### Drive file disappears manually\n\nAccess returns a controlled missing-file state rather than silently retrying forever.\n\n## Personal Google Drive note\n\nThe current intended storage account is a personal Google account with a 5 TB Google One plan.\n\nThis is usable for an initial deployment, but a Google Workspace Shared Drive is a stronger long-term ownership model because content belongs to the organization rather than one person's account.\n\n## Migration\n\nMigration is deliberately staged:\n1. Keep Supabase Storage active.\n2. Add Google metadata fields.\n3. Test Google uploads.\n4. Test Google downloads.\n5. Test deletes and renames.\n6. Migrate existing files.\n7. Verify every migrated record.\n8. Switch new writes to Google Drive.\n9. Only after verification remove old Supabase Storage dependencies.\n\n## Safety rule\n\nDrive permissions are not the application's authorization boundary.\n\nSupabase Auth + RLS + application role rules remain authoritative for every file operation.
