# PDF Compression — Phase 3

## What is now complete

Phase 3 adds real image/raster recompression for image-heavy and scanned PDFs while preserving the Phase 2 safety pipeline.

### Processing flow

1. The browser uploads the original PDF unchanged.
2. The existing pdf_compression_jobs row is created and claimed.
3. The Edge Function stages the source in the private tenant/job temporary bucket.
4. The Edge Function creates short-lived signed download/upload capabilities.
5. A dedicated Vercel Node function receives only the job ID, compression profile, signed source URL, signed temporary-output upload URL, and output path.
6. The Vercel worker uses the Apache-2.0 sharp engine to recompress supported PDF image XObjects as JPEG.
7. Large raster images are conservatively downsampled to the profile's maximum dimension before JPEG encoding.
8. The worker validates the generated PDF and refuses to stage a candidate unless it is valid and strictly smaller than the source.
9. The Edge Function downloads the candidate from the private staging bucket and validates it again, including page count.
10. The source object timestamp is checked again before replacement.
11. Only a validated smaller candidate replaces the original.
12. Job telemetry records image counts and raster-byte reduction.
13. Temporary objects are deleted in finally.

## Supported raster inputs

The raster engine intentionally handles only conservative image classes:

- JPEG (DCTDecode) image streams using DeviceRGB or DeviceGray.
- Flate-compressed (FlateDecode) 8-bit DeviceRGB / DeviceGray image streams that decode to the expected raw byte length.

The engine skips image masks, soft masks, explicit masks, custom decode arrays, decode parameters/predictors, indexed/CMYK/Lab/separation color spaces, unsupported filters, non-8-bit images, and oversized/decompression-bomb-style images. Skipping is safer than silently changing document appearance or transparency semantics.

The engine does not flatten complete PDF pages. Text, vectors, page structure, annotations and forms therefore remain as PDF objects instead of being converted into page screenshots.

## Profiles

| Profile | JPEG quality | Max image dimension |
| --- | ---: | ---: |
| recommended | 72 | 2400 px |
| extreme | 55 | 1700 px |
| less | 82 | 3200 px |

These are image-oriented profiles, not a promise of a fixed percentage reduction. A candidate is accepted only when the complete resulting PDF is smaller.

## Licensing and deployment

The Phase 3 image engine uses sharp, which is Apache-2.0 licensed. The heavy native image processing intentionally runs in a Vercel Node function rather than the Supabase Edge runtime. Supabase documents a 256 MB Edge memory limit, 2 seconds of active CPU time per request, and plan-dependent wall-clock limits; its documentation specifically lists sharp/libvips among Node libraries that cannot be used in the Edge runtime.

The Vercel worker does not receive raw PDF bytes in its request and does not hold the Supabase service-role key. It receives short-lived signed Storage capabilities generated by the trusted Edge Function. The worker validates that those URLs belong to the project's Supabase Storage host and are the expected signed download/upload endpoints.

## Safety guarantees

- Original PDF remains untouched until the candidate passes validation.
- Candidate must be strictly smaller than the source.
- Page count must remain unchanged.
- The source object must not change while compression is running.
- Raster candidates are stored in a private per-job staging path.
- Signed URLs expire and are never exposed to the browser.
- Raster worker failures fall back to the Phase 2 structural optimizer.
- The Phase 2 structural optimizer remains the final optimization fallback.
- Failed or unchanged jobs keep the original file.
- Image-level telemetry is stored on the compression job.
- The first processing attempt is numbered 1; retries increment the attempt number instead of resetting it.

## Runtime boundary

The application keeps the existing 50 MB PDF processing boundary. Vercel Functions are used for the CPU-heavy raster stage, while Supabase remains the authorization, queue, validation and source-of-truth layer.

The worker is exposed through the production route:

https://learners-guide.vercel.app/api/pdf-compression-worker

The Supabase function can override this route with the PDF_COMPRESSION_RASTER_WORKER_URL environment variable for staging or another trusted Vercel deployment.

## Phase 3 boundary

Phase 3 is the first production implementation in Learner's Guide that can materially reduce the size of image-heavy/scanned PDFs through actual raster recompression.

It is intentionally not a full PDF rendering engine. PDFs with complex transparency, uncommon color spaces, unsupported filters or unusual image predictors are skipped at the image level and continue through the safe structural fallback.

The existing tenant/job/storage contract remains unchanged so the future SaaS tenant registry can replace the compression-specific tenant bridge without redesigning the compression engine.
